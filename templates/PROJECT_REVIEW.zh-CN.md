# 项目审查

[English](PROJECT_REVIEW.md)

使用 Agentic Open-Source Engineering Methodology 快速暴露目标项目中重要的工程缺口。

目标项目可以公开或私有、位于本地或远程，也不要求必须使用 Git。本审查只应用真正与项目相关的方法论维度。它是一种诊断工具，不是认证、合规审计或通用成熟度排行榜。

由 Agent 执行审查时，应遵循 canonical [`AGENT_REVIEW_PROTOCOL.md`](../AGENT_REVIEW_PROTOCOL.md)。

## 先判断适用性

评分之前，先把每个审查维度标记为：

- **Material — 核心相关**：会实质影响项目结果或风险；
- **Relevant — 一般相关**：值得检查，但属于次要因素；
- **N/A — 不适用**：对当前目标项目没有实质意义。

`N/A` 不是缺陷，也不会扣分。不得仅仅因为方法论存在某条原则，就人为制造一个项目问题。

如果某个适用维度缺少足够证据，应标记为 **NE — Not Enough Evidence（证据不足）**，而不是猜测数字。

## 诊断评分尺度

对于证据充分的适用维度：

- **0 — Critical gap：严重缺口**
- **1 — Weak：明显薄弱**
- **2 — Partial：部分满足**
- **3 — Good：当前需求下处理良好**
- **4 — Strong：明确、适度且有充分证据支撑**

每个数字分数同时标注 **High / Medium / Low** 证据置信度。

由 Agent 执行时，`Material` 维度权重为 `2`，`Relevant` 维度权重为 `1`。只有至少 70% 的适用加权维度具有足够证据时，才给出总分。精确公式与输出协议见 Agent Review Protocol。

## 1. 项目清晰度与结果

- 项目真正要解决什么问题？
- 主要用户、操作者、维护者或贡献者是谁？
- 哪些项目结果重要到足以影响工程 trade-off？
- 哪些明确约束或质量属性塑造了项目？

## 2. Agent 上下文与人类责任

当 AI Agent 实质参与开发或运行时：

- Agent 能否在不依赖隐式本地知识的情况下识别项目结构、关键命令、约束和 Definition of Done？
- 在确有价值时，是否存在简洁的 `AGENTS.md` 或等价项目指令？
- 当某个子系统确实存在特殊不变量时，是否把规则放在接近其作用域的位置？
- 重要决策与发布结果是否仍然由人承担责任？

如果 AI Agent 并未实质参与目标项目，本维度可以是 `N/A`。

## 3. 开放与协作边界

当公开发布、外部复用、开源贡献、互操作或外部协作属于项目目标时：

- License 或复用边界是否清晰？
- 在相关场景下，公开接口、格式和贡献路径是否容易理解？
- 是否存在有意保持私有、embargoed、proprietary 或不应进入公开边界的内容？
- public/private boundary 是否由项目有意识决定，而不是偶然形成？

对于明确保持封闭、且没有公开发布或外部协作目标的内部项目，本维度可以是 `N/A`。

## 4. 用户主权与隐私

当项目会接触用户数据、凭证、私有文件、个人环境或外部服务时：

- 项目能够访问哪些敏感信息或用户控制的材料？
- 哪些数据会离开用户环境？为什么？
- Agent、自动化与外部服务是否只拥有完成任务所需的权限？
- 在合理情况下，用户能否理解并控制重要的数据与执行选择？

## 5. 本地 / 远程边界

当项目存在有意义的运行时、数据流或托管服务行为时：

- 哪些能力在本地运行，哪些依赖远程服务？
- 这种边界是否由能力、易用性、成本、维护或隐私需求合理支撑？
- 用户能否理解重要外部数据流与依赖？

如果项目不存在实质 local/remote 执行边界，本维度可以是 `N/A`。

## 6. 可移植性与锁定

当可替换 provider、模型、Agent、云平台、格式或工具链确实重要时：

- 哪些属于硬依赖？
- 每一项 lock-in 是否有意识接受？
- 增加可替换边界的收益是否足以证明复杂度？
- 在真正需要可移植性的地方，provider-specific optimization 是否得到合理隔离？

不得仅为了提高可移植性分数而推荐没有价值的抽象层。

## 7. 依赖纪律

对于重要依赖：

- 它解决什么问题？
- 自行实现是否会明显更差？
- 安装、维护、安全、可移植性和替换成本如何？
- 依赖负担是否与项目真实复杂度相称？

## 8. 渐进式易用性

对于项目真正面向的用户或贡献者：

- 他们能否快速判断项目是什么、是否适合自己？
- 是否存在最小且有价值的尝试、采用或操作路径？
- 主要假设与限制是否可见？
- 在合理情况下，高级细节是否与初始路径分离？

不得用 newcomer-friendly 的目标去评价一个明确只服务内部专家、且从未承诺新手体验的项目。

## 9. 可验证性

- 哪些命令、测试、证据或可复现检查能够说明重要行为或声明可以接受？
- 重要声明在合理情况下是否可测试、可复现或可检查？
- 验证体系是否与项目真实风险相称？
- 在“成功执行”和“证明正确”存在区别时，项目是否明确区分两者？

## 10. 可逆性

- 修改是否保持在可审查、合理聚焦的范围？
- 哪些操作具有破坏性或难以撤销？
- 高风险修改在合理情况下是否具有 backup、dry-run、rollback、recovery 或 migration path？
- 生成产物与临时状态是否在确有价值时得到隔离，以控制 blast radius？

## 11. 例外与证据

对于重要的非默认选择，应判断其他开发者或 Agent 能否理解：

`Default → Conflict → Trade-off → Exception → Evidence → Revisit`

偏离默认原则并不自动意味着缺陷。必须区分真实工程缺口与有充分理由的项目特定 trade-off。

普通决策使用清晰的 PR 或 commit 说明即可。只有真正值得长期保存的决策才使用 [Decision Record](DECISION_RECORD.md)。

## 12. 审查结果

一个有价值的审查结果应包含：

- **Dimension Scorecard**：展示适用性、分数、置信度与主要证据；
- 只有证据覆盖充分时才给出的 **Diagnostic Score / 100**；
- **Evidence Coverage**：让用户知道有多少适用项目内容真正获得了证据支持的判断；
- **现在最值得修复的高价值缺口**；
- **应当保持不变的已接受 trade-off**；
- 在作出决定前仍然需要补充的 **Evidence Needed**；
- 因修复成本高于当前价值而**有意延后的事项**；
- 简短、有优先级的 **下一步行动**。

分数只是摘要，不是结论。高总分不能抵消某个严重单点问题，也不应把不同类型项目的分数机械地横向比较。
