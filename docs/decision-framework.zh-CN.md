# 决策框架

[English](decision-framework.md)

本方法论把核心原则视为强默认偏好，而不是绝对规则。本框架用于处理例外，使方法论既不滑向僵化教条，也不退化成无法约束工程行为的模糊偏好。

## 决策闭环

使用：

`Default → Conflict → Trade-off → Exception → Evidence → Revisit`

### 1. Default — 明确默认原则

首先确定与当前问题相关的默认原则。默认值的意义在于减少重复争论，让不同项目与不同 Agent 的行为更加一致。

### 2. Conflict — 识别真实冲突

明确真正发生的冲突，例如：

- 可移植性 vs 特定 provider 的能力优势；
- 本地执行 vs 易用性或算力要求；
- 减少依赖 vs 复用成熟基础设施；
- 新手简单性 vs 高级配置能力；
- Agent 快速执行 vs 可审查性与安全性。

不得为了给已经偏好的方案找理由而虚构冲突。

### 3. Trade-off — 分析实际权衡

比较真正重要的工程后果，而不是统计每个方案“满足了几条原则”。

根据任务性质考虑：

- 用户价值；
- 正确性与质量；
- 隐私与安全；
- 可靠性与可验证性；
- 性能；
- 可维护性；
- 运维与认知复杂度；
- 可移植性与锁定成本；
- 可逆性；
- 短期与长期成本。

### 4. Exception — 必要时允许例外

当证据表明非默认方案能够实质改善项目结果时，可以选择例外。

例外的作用范围应尽可能小。不得因为一次特殊情况，就把局部例外直接推广成新的项目级规则。

### 5. Evidence — 保留足够证据

记录足够的理由，让其他开发者或 Agent 能够理解为什么存在这次偏离。

证据不必总是重型文档。根据影响范围，可以是：

- PR 描述；
- 简短 decision note；
- benchmark；
- 测试结果；
- issue 讨论；
- 设计记录。

影响越大、越难回滚的例外，需要越强的证据。

### 6. Revisit — 条件变化后重新评估

例外只是当前条件下的工程决策，而不是永久真理。

出现以下情况时应重新评估：

- 底层工具或模型发生变化；
- 维护成本持续上升；
- 原始约束已经消失；
- 新证据推翻原有理由；
- 一个局部例外开始扩散到原本范围之外。

## 决策质量优先于“原则计数”

一个方案不会因为满足了更多条命名原则就自动更好。原则的作用是暴露重要工程问题，而不是建立评分游戏。

当原则冲突时，应优先选择最能保护用户价值、项目质量、安全、维护性以及项目明确目标的方案。

## 决策记录应与风险成比例

记录强度应与影响相匹配：

- **低风险：** 正常 commit 或 PR 说明通常足够；
- **中风险：** 明确写出 default、conflict、trade-off 和 exception；
- **高风险：** 应保留更持久的证据、备选方案、风险、回滚策略和 revisit 条件。

高风险示例包括：破坏性 migration、隐私或安全边界变化、provider lock-in、仓库 visibility 修改、重大依赖承诺以及不可逆的 Git history 修改。

## 修改方法论本身之前

修改核心原则前应先回答：

1. 当前到底存在什么反复出现、且现有方法论处理不好的工程问题？
2. 它是否具有跨项目价值，而不是一次性偶发现象？
3. proposed change 实际上属于 Principle、Decision Rule 还是 Practice？
4. 是否只需要澄清现有原则，而无需增加新原则？
5. 它是否来自长期工程属性，而不是短期工具趋势？
6. 有哪些真实项目证据支持修改？

如果这些问题无法得到有力回答，优先保持核心方法论不变。
