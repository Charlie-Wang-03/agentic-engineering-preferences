# 项目审查

[English](PROJECT_REVIEW.md)

用于快速暴露高度使用 AI Agent 的开源项目中最重要的工程缺口。它是诊断工具，不是认证清单，也不用于计算“成熟度分数”。

只回答真正与项目相关的问题。简短但明确的判断，比为了流程完整而增加文档更有价值。

## 1. 项目目的与用户

- 项目真正要解决什么问题？
- 主要用户或贡献者是谁？
- 哪些项目结果重要到足以影响工程 trade-off？

## 2. Agent 上下文

- Coding Agent 能否在不依赖隐式本地知识的情况下识别仓库结构、关键命令、约束和 Definition of Done？
- 在确有价值时，是否存在简洁的 `AGENTS.md` 或等价仓库指令？
- 当某个子系统确实存在特殊不变量时，是否把规则放在接近其作用域的位置？

## 3. 开源边界

- License 是否清晰？
- 在相关场景下，公开接口、格式和贡献路径是否容易理解？
- 是否存在有意保持私有、embargoed、proprietary 或不应进入公开边界的内容？

## 4. 用户控制权与隐私

- 项目可能接触哪些用户数据、凭证、私有文件或机器专属信息？
- 哪些数据会离开用户环境？为什么？
- Agent、自动化与外部服务是否只拥有完成任务所需的权限？

## 5. 本地 / 远程边界

- 哪些能力在本地运行，哪些依赖远程服务？
- 这种边界是否由能力、易用性、成本、维护或隐私需求合理支撑？
- 用户能否理解重要的外部数据流与依赖？

## 6. 可移植性

- 哪些模型、Agent、provider、云服务、平台或工具链属于硬依赖？
- 每一项 lock-in 是否有意识地接受？
- 增加可替换边界的收益是否足以证明其复杂度？

## 7. 依赖

对于重要依赖：

- 它解决什么问题？
- 自行实现是否会明显更差？
- 安装、维护、安全、可移植性和替换成本如何？

## 8. 易用性

新用户能否快速判断：

1. 这个项目是什么；
2. 是否适合自己；
3. 最小且有价值的尝试或采用方式；
4. 主要假设与限制；
5. 高级细节在哪里。

## 9. 可验证性

- 哪些命令或证据能够说明一次修改可以接受？
- 重要声明在合理情况下是否可测试、可复现或可检查？
- 验证体系是否与项目真实风险相称？

## 10. 可逆性

- 修改是否保持在可审查、合理聚焦的范围？
- 哪些操作具有破坏性或难以撤销？
- 高风险修改在合理情况下是否具有 backup、dry-run、rollback 或 recovery path？

## 11. 例外与证据

对于重要的非默认选择，其他开发者或 Agent 能否理解：

`Default → Conflict → Trade-off → Exception → Evidence → Revisit`

普通决策使用清晰的 PR 或 commit 说明即可。只有真正值得长期保存的决策才使用 [Decision Record](DECISION_RECORD.md)。

## 12. 审查结果

不要计算分数，只总结：

- **现在最值得修复的高价值缺口**；
- **应当保持不变的已接受 trade-off**；
- **需要更多证据才能决定的事项**；
- 因为修复成本高于价值而**有意延后的事项**。
